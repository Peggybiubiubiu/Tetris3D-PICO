# Tetris3D PICO native window host

PICO Spatial SDK 6.1.9 host generated by pico-cli, with the original Unity game imported as unityLibrary. Package remains com.example.tetris3d.pico.

Window layout: game center; live score/time/difficulty right; emotion/focus demo left; focus progress above left; EEG below game; email account on demand to the right of the score window. Stable IDs/tags anchor layout to TetrisGame, never current focus. Users can move windows themselves. Collapsing BCI closes auxiliary windows and disables modulation.

EEG is explicitly synthetic: 32 channels, 256 Hz, 2 seconds, microvolt-like demonstration signals. Focus/mood sliders are demo input, not EEG-derived estimates. EegDataSource defines a future device adapter boundary; no actual hardware driver exists. BciReading rejects stale, future, non-finite and out-of-range samples.

Unity owns scoring, effective play time and drop cadence. SpatialGameBridge publishes snapshots to GameStateBridge. Focus 0..1 maps to 1..2x drop speed; mood low mixes block color toward white (max 65%). Inputs slew at 0.5 normalized units/sec; after 3 sec without input or when disabled, ordinary gameplay is restored. Pause stops effective play time.

Email login and six-digit email-code registration are UI/interface only. UnconfiguredAccountRepository does not send mail or create accounts and returns an explicit unavailable message. Passwords/codes are never saved to preferences and are cleared on submit/close. Add a real HTTPS provider behind AccountRepository for deployment.

Build on an ASCII path (for Unity/Android tools). Sync this host to /tmp/Tetris3D-SpatialHost and use JDK 21 with ./gradlew assembleDebug testDebugUnitTest. Unity changes must be rebuilt with Assets/Editor/PicoBuild.cs from the parent Unity project; refresh unityLibrary/src/main/assets and jniLibs before host packaging. The parent Unity-only APK is not the native-window build.

Web design visual review was blocked by browser policy. User explicitly authorized direct native implementation and simulator verification. Static design checks passed; do not claim web visual review passed. Actual runtime verification is recorded separately.

## Simulator verification (2026-11-05)

Debug APK compiled and installed on PICO OS 6.1 emulator-5554. Six JVM unit tests passed. Native screenshots in ../Builds/Spatial show the Unity game, separate left BCI and right metrics windows, and the upper part of the EEG window with live synthetic traces. Play was invoked through the same application handler using a debug-only preview launch extra; gameplay and elapsed time were visibly confirmed. The focus window is created above the left board, outside most of the forward screenshot. Full focus/account visual review and manual fold/reopen interactions remain unverified because simulator spatial input could not be automated reliably.

Instrumentation reached the game scene assertions, but the runner ended with “Process crashed” during Unity Activity teardown, so connected tests are NOT recorded as passing. A subsequent ordinary launch remained alive and rendered the windows. Do not interpret this as comprehensive lifecycle validation.

For an explicit local demo launch, a debuggable build accepts the boolean Activity intent extra `preview=true`: after Unity is ready it opens EEG/focus, enables synthetic BCI, and starts gameplay. Normal launches do not automatically start the game or enable BCI. Release builds ignore this extra.
